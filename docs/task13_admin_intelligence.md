# Task 13 — Admin Intelligence Dashboard Backend Documentation

## 1. Overview & Purpose
Task 13 establishes the backend and API layer for the real Lead Magnet Admin Intelligence Dashboard. It consolidates canonical data generated by Tasks 8–12 (`user_profiles`, `customer_features`, `customer_lead_state`, `marketing_automation_events`, `marketing_communications`, `admin_notifications`, `orders`) into real-time, read-only analytical endpoints for store administrators.

---

## 2. API Endpoints Reference

All endpoints are read-only (`GET` requests) and require `@admin_required` authorization (returning `401 Unauthorized` if unauthenticated or `403 Forbidden` for standard customer tokens).

| Endpoint Path | Purpose | Parameters | Response Payload |
|---|---|---|---|
| `GET /api/admin/intelligence/overview` | Real-time aggregate KPIs across customers, lead states, and marketing dispatches | None | `{ "customers": {...}, "leads": {...}, "marketing": {...}, "updated_at": "..." }` |
| `GET /api/analytics/overview` | Backward compatible overview endpoint for existing admin components | None | Extends legacy payload with canonical customer, lead, and marketing metrics |
| `GET /api/admin/intelligence/leads` | Customer-level lead directory (1 row per customer) | `qualification_status`, `segment`, `sort_by`, `sort_order`, `page`, `limit` | `{ "items": [...], "page": 1, "limit": 25, "total": N, "pages": P }` |
| `GET /api/admin/intelligence/customers/<customer_id>` | Unified customer intelligence profile deep-dive | None | `{ "customer": {...}, "behavior": {...}, "lead": {...}, "orders": [...], "marketing": {...} }` |
| `GET /api/admin/intelligence/lead-distribution` | Lead distribution breakdown across segments (`Hot`/`Warm`/`Cold`) and status | None | `{ "total": N, "segments": {...}, "qualification": {...} }` |
| `GET /api/admin/intelligence/recent-leads` | Feed of customers who recently transitioned to qualified lead status | `page`, `limit` | `{ "items": [...], "page": 1, "limit": 10, "total": N, "pages": P }` |
| `GET /api/admin/intelligence/marketing-activity` | Feed of recent marketing automation events and channel dispatches | `page`, `limit` | `{ "items": [...], "page": 1, "limit": 25, "total": N, "pages": P }` |
| `GET /api/admin/intelligence/notifications` | Feed of internal admin notification logs | `read`, `page`, `limit` | `{ "items": [...], "page": 1, "limit": 25, "total": N, "pages": P }` |

## 3. Data Sources & Counting Definitions

### 3.1 Canonical Collections Used
- **`user_profiles`**: Primary source for canonical customer identities, names, emails, roles, and creation timestamps.
- **`customer_features`**: Canonical source for aggregated behavioral features (sessions, total time, page views, cart value, orders count, etc.).
- **`customer_lead_state`**: Canonical source for lead qualification status (`qualified`, `not_qualified`), lead scores (0–100), probabilities, segments (`Hot`, `Warm`, `Cold`), and qualification timestamps.
- **`marketing_automation_events`**: Canonical source for qualification transition events.
- **`marketing_communications`**: Canonical source for communication attempts (`sent`, `failed`, `skipped`).
- **`admin_notifications`**: Internal administrative notifications log.
- **`orders`**: Customer order history.

*Note: The legacy `leads` collection is historical model output and is NOT used as a customer identity or lead state count source.*

### 3.2 Customer Counting Rules
- **Total Customers**: Total count of documents in `user_profiles` (excluding `role: "admin"`).
- **Active Today**: Customers whose `last_active_at` date matches today's UTC ISO date prefix (`YYYY-MM-DD`).
- **New Today**: Customers whose `created_at` date matches today's UTC ISO date prefix (`YYYY-MM-DD`). If `created_at` timestamps are inconsistent or missing, returned as `null`.

### 3.3 Qualified Lead Definition
A qualified lead is strictly defined as any customer record in `customer_lead_state` where `qualification_status == "qualified"`.

---

## 4. Directory Listing, Sorting, Filtering & Pagination

### 4.1 One Row Per Customer Contract
`GET /api/admin/intelligence/leads` enforces a strict one-row-per-customer structure. It queries `customer_lead_state` and joins customer identity and last communication attempt metadata. It excludes `not_qualified` customers by default.

### 4.2 Filtering & Sorting Parameters
- **`qualification_status`**: `"qualified"` (default), `"not_qualified"`, or `"all"`.
- **`segment`**: `"Hot"`, `"Warm"`, `"Cold"`, or `"all"`.
- **`sort_by`**: `"lead_score"` (default), `"lead_probability"`, `"last_scored_at"`, `"first_qualified_at"`.
- **`sort_order`**: `"desc"` (default) or `"asc"`.

### 4.3 Safe Bounded Pagination
- `page`: Minimum 1.
- `limit`: Bounded between 1 and 100 (default 25).
- Returns total item count and total calculated pages to prevent out-of-bounds offset queries.

---

## 5. Security & Data Sanitization
- **Admin Authentication**: All endpoints require `@admin_required`. Invalid JWT tokens return `401 Unauthorized`; non-admin user tokens return `403 Forbidden`.
- **Data Sanitization**: `get_customer_intelligence_detail` strips all sensitive security credentials (`password`, `password_hash`, `hashed_password`, `token`, `secret`, `jwt`).
- **Input Validation**: `customer_id` path parameters are validated via `ObjectId.is_valid()`, returning `400 Bad Request` for malformed IDs and `404 Not Found` for non-existent customers.

---

## 6. Performance & Read-Only Safety
- **Read-Only Guarantee**: All intelligence routes handle `GET` requests exclusively and perform zero database write or mutation operations.
- **Aggregations**: Database metrics utilize indexed PyMongo counts (`count_documents`) and bounded paginated cursors (`skip` + `limit`) to prevent unbounded memory allocation.
- **N+1 Avoidance**: Batch joins for customer profiles and last communications are executed per paginated page (maximum 100 items).
